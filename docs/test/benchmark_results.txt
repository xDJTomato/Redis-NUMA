## 5. 性能对比分析
----------------------------------
NUMA内存池 vs 无内存池:
- SET性能: 166K vs 25K = 6.6x提升 ✓
- GET性能: 166K vs 27K = 6.1x提升 ✓
- 延迟优化: p50从1-2ms降至0.15-0.2ms

NUMA内存池 vs 标准Redis(jemalloc):
- SET性能: 166K vs 150K = 1.1x (持平或略优)
- GET性能: 166K vs 140K = 1.2x (略优)

## 7. 结论
----------------------------------
✓ NUMA内存池成功实现，性能达到预期
✓ 小对象分配（≤512字节）性能提升5-6倍
✓ 与标准Redis性能相当或略优
✓ 所有数据结构操作正常
✓ Pipeline模式下可达百万级QPS

内存池设计合理：
- 64KB chunk大小适中
- 8级大小分类覆盖常见场景
- 16字节PREFIX开销可接受
- from_pool标记支持差异化释放策略

## 8. NUMAflow 公平评测（QEMU 不可用环境，本次新增）
----------------------------------

由于开发机为 16GB Windows（无 libnuma / 无异构内存 / 无 QEMU），本仓库新增了
纯 C11 的 NUMAflow 评测框架（numaflow/），在可移植 libnuma 仿真拓扑上复现同一条
访问轨迹，公平比较各调度策略。DRAM 容量约束为工作集约 50%，迫使策略做取舍。

zipf / 3000 keys / 120000 访问 / budget=256 / 2 节点（dram0 + cxl1）:

  策略             | 本地命中率 | 净代价(ns) | 迁移次数
  ----------------|-----------|-----------|--------
  Baseline (noop) | 0.0%      | 305.0M    | 0
  Composite LRU   | 81.2%     | 134.5M    | 2187
  TinyLFU         | 79.3%     | 105.9M    | 832
  CAAT（新默认）  | 91.0%     | 84.8M     | 2310

结论: CAAT 净代价比最佳基线（TinyLFU）低约 20%，比 Composite LRU 低约 37%；
      它通过「晋升 + 降级」在容量约束下维持 DRAM 最优驻留，是新的默认策略。

订正（本次新增，测试时间: 2026-08-19，见 docs/new/09-architecture-decisions.md
ADR-09）: 上表数字已用修复过两个 bug 之后的二进制重新生成（此前一版数字
——命中率 91.1%、迁移次数 2422——出自还带有其中一个 bug 的中间状态，另有一版
更早提交到 results/bench_zipf.json 的数字命中率只有 84.6%，出自两个 bug 都还
在的状态）。这两个 bug 是：① NUMAflow 桥接（src/numa_flow.c）从未真正调用过
`nf_tracker_observe()`，导致 TinyLFU/CAAT 依赖的频率估计在真实 Redis 路径下恒
为 0；② CAAT 旧版是单条线性 DAG 链，降级阶段的变更会被紧跟着的晋升阶段过滤器
丢弃出图的终止节点，导致该次降级从未真正传给宿主执行。两者均已修复并有独立
harness 验证（细节见 ADR-09）。

**重要补充**：CAAT 相对 Composite LRU/TinyLFU 的优势是**工作负载依赖**的，不是
全面成立的。用仓库自带的四个基准工作负载全量复测：

  工作负载  | CAAT vs Composite LRU | CAAT vs TinyLFU | CAAT 本地命中率
  ---------|------------------------|-------------------|------------------
  zipf     | 净代价低 36.9%（更优） | 净代价低 19.9%（更优） | 91.0%
  hotspot  | 净代价低 39.5%（更优） | 净代价低 16.4%（更优） | 89.6%
  uniform  | 净代价高 31.1%（更差） | 净代价低 12.2%（更优） | 49.0%
  temporal | 净代价高 3.3%（更差）  | 净代价低 16.4%（更优） | 57.3%

CAAT 在有明显冷热分层的负载（zipf/hotspot）上明显更优，但在访问接近均匀分布、
没有真正"冷"数据的 uniform 负载上反而更差——`demote_cold` 主动搬走"冷"数据这个
动作，在没有真正冷热差异时变成纯粹的迁移开销浪费。ADR-08 把 CAAT 设为内核默认
这个决策本身不需要撤销（真实 Redis 场景的访问分布多数偏态，接近 zipf/hotspot），
但引用"CAAT 更优"时应注明是在哪类工作负载下更优，不是无条件成立。

复现:  cd numaflow && make && make bench && make report   # 生成 results/report.html
       cd numaflow && make test             # 全部单元/冒烟/桥接测试

## 9. YCSB 带宽/负载基准（本次新增，测试时间: 2026-08-19）
----------------------------------

此前的验证会话因沙箱环境没有 JDK 而跳过了这一层（见 TESTING.md 第 4 项）。本次
补装了一份便携式 JDK 17（Temurin，解压到 ~/.local/opt/jdk-17，无需 root）和便携
式 Maven 3.9.9，跑通了 tests/ycsb/run_bw_benchmark.sh 和 tests/ycsb/run_ycsb.sh。

跑的过程中遇到、并修复了两个和"沙箱只有 1 个 NUMA 节点"相关的环境问题：

1. `run_bw_benchmark.sh` 默认 `--process-nodes 0,2`（把 Redis 进程绑定到 NUMA
   节点 0 和 2），但本机 `numactl --hardware` 只有 `available: 1 nodes (0)`，
   `numactl --cpunodebind=0,2` 直接报错退出。改用脚本自带的
   `--process-nodes all`（取消节点绑定）后正常运行——这是一个真实存在、值得记住
   的坑：任何只有 1 个物理 NUMA 节点的机器上跑这个脚本，都需要这个参数。
2. 官方 YCSB 0.17.0 发行包里 `bin/ycsb`（Python 版命令行入口）是 Python 2 语法
   （`except Foo, err:`），本机只有 python3，运行会直接 SyntaxError。`bin/ycsb.sh`
   （Java 版入口，CLI 参数完全一致）不受影响——这也是 run_bw_benchmark.sh 自己的
   注释里已经提到、并主动绕开的同一个问题。把解压出来的 `bin/ycsb`（第三方发行包
   的一部分，不在本仓库版本控制中）换成一个转发到 `ycsb.sh` 的 shim 后解决。

### run_bw_benchmark.sh --process-nodes all（3 阶段）

  ----------------------------|---------------
  Phase 1 Fill（填充）        | 9,688

## 10. 迁移策略全量对比：Vanilla / Noop / Composite LRU / TinyLFU（本次新增，测试时间: 2026-08-19）
----------------------------------

新增 `tests/ycsb/run_algorithm_comparison.sh`，把 run_bw_benchmark.sh 里已有的
`--tinylfu` 开关补齐了一个对称的 `--no-migrate`（只关 Slot 1，不开 Slot 2，得到
纯 noop 基线），再串联已存在的 `run_bw_benchmark_vanilla.sh`，四组跑同一份
bw_saturate 三阶段负载（Fill→Hotspot→Sustain），maxmem 统一为 8gb（此前
vanilla 脚本默认 8gb、NUMA 脚本默认 3500mb，四组必须一致才是单一变量对比）。

顺带修了一个真实 bug：`run_bw_benchmark_vanilla.sh` 头部注释写着"Phase 参数与
CXL 版完全一致"，但 PHASE2_OPS/PHASE3_OPS 实际是 2M/6M，主脚本是 4M/4M——两边
早就不一致了，这次统一改成 4M/4M。另外 `visualize_bw_benchmark.py` 的
NAMED_PALETTE 缺 "Redis-NUMA (Noop)" 这个新标签，索引取模后刚好撞上了
"Vanilla Redis" 的同一个绿色，两条曲线在图上完全重叠分不清——补充了独立的橙色。

  组                          | Fill (ops/sec) | Hotspot (ops/sec) | Sustain (ops/sec)
  ----------------------------|----------------|--------------------|-------------------
  Vanilla Redis 7.2.6         | 22,733         | 131,419            | 131,713
  Redis-NUMA (Composite LRU)  | 41,549         | 123,977            | 126,478
  Redis-NUMA (Noop)           | 44,086         | 134,821            | 134,431
  Redis-NUMA (TinyLFU)        | 40,378         | 121,655            | 122,952

结论: 这是单节点沙箱环境（`numactl --hardware` 只有 1 个 NUMA 节点），没有真实的
跨节点带宽/延迟差异可利用，所以四组的量级基本相当，差异主要来自 NUMA 内存池分配器
本身的开销（Fill 阶段 NUMA 版比 vanilla 快 1.8-2x，是内存池 O(1) 分配 vs
jemalloc 的差异，不是迁移策略的效果）与迁移策略的运行时开销（Composite LRU /
TinyLFU 在 Hotspot/Sustain 阶段比 Noop 基线慢 6-10%，这是迁移扫描本身占用的
CPU/锁开销）。要看到迁移策略在真实多 NUMA 节点/CXL 环境下的收益（跨节点访问延迟
差异足够大时，迁移换来的本地化命中率提升才能覆盖迁移开销），需要在有 ≥2 个物理
NUMA 节点或 CXL 设备的机器上重跑本对比。

结果目录: Results/algorithms_20260819_162940/
（comparison_report.png、comparison_report_latency.png、summary.txt，以及
vanilla/ noop/ composite_lru/ tinylfu/ 四个子目录下的完整 metrics.csv 和
YCSB 原始输出）

复现:  cd tests/ycsb && ./run_algorithm_comparison.sh
