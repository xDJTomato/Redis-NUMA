## 7. 结论
----------------------------------
✓ NUMA内存池成功实现，性能达到预期
✓ 小对象分配（≤512字节）性能提升5-6倍
✓ 与标准Redis性能相当或略优
✓ 所有数据结构操作正常
✓ Pipeline模式下可达百万级QPS

内存池设计合理：
- 64KB chunk大小适中
- 8级大小分类覆盖常见场景
- 16字节PREFIX开销可接受
- from_pool标记支持差异化释放策略

## 8. NUMAflow 公平评测（QEMU 不可用环境，本次新增）
----------------------------------

由于开发机为 16GB Windows（无 libnuma / 无异构内存 / 无 QEMU），本仓库新增了
纯 C11 的 NUMAflow 评测框架（numaflow/），在可移植 libnuma 仿真拓扑上复现同一条
访问轨迹，公平比较各调度策略。DRAM 容量约束为工作集约 50%，迫使策略做取舍。

zipf / 3000 keys / 120000 访问 / budget=256 / 2 节点（dram0 + cxl1）:

  策略             | 本地命中率 | 净代价(ns) | 迁移次数
  ----------------|-----------|-----------|--------
  Baseline (noop) | 0.0%      | 305.0M    | 0
  Composite LRU   | 81.2%     | 134.5M    | 2187
  TinyLFU         | 79.3%     | 105.9M    | 832
  CAAT（新默认）  | 91.1%     | 84.9M     | 2422

结论: CAAT 净代价比最佳基线（TinyLFU）低约 20%，比 Composite LRU 低约 37%；
      它通过「晋升 + 降级」在容量约束下维持 DRAM 最优驻留，是新的默认策略。

复现:  cd numaflow && make && make report   # 生成 results/report.html（SVG/HTML 报告）
       cd numaflow && make test             # 40 项单元检查 + 集成冒烟测试

## 9. YCSB 带宽/负载基准（本次新增，测试时间: 2026-08-19）
----------------------------------

此前的验证会话因沙箱环境没有 JDK 而跳过了这一层（见 TESTING.md 第 4 项）。本次
补装了一份便携式 JDK 17（Temurin，解压到 ~/.local/opt/jdk-17，无需 root）和便携
式 Maven 3.9.9，跑通了 tests/ycsb/run_bw_benchmark.sh 和 tests/ycsb/run_ycsb.sh。

跑的过程中遇到、并修复了两个和"沙箱只有 1 个 NUMA 节点"相关的环境问题：

1. `run_bw_benchmark.sh` 默认 `--process-nodes 0,2`（把 Redis 进程绑定到 NUMA
   节点 0 和 2），但本机 `numactl --hardware` 只有 `available: 1 nodes (0)`，
   `numactl --cpunodebind=0,2` 直接报错退出。改用脚本自带的
   `--process-nodes all`（取消节点绑定）后正常运行——这是一个真实存在、值得记住
   的坑：任何只有 1 个物理 NUMA 节点的机器上跑这个脚本，都需要这个参数。
2. 官方 YCSB 0.17.0 发行包里 `bin/ycsb`（Python 版命令行入口）是 Python 2 语法
   （`except Foo, err:`），本机只有 python3，运行会直接 SyntaxError。`bin/ycsb.sh`
   （Java 版入口，CLI 参数完全一致）不受影响——这也是 run_bw_benchmark.sh 自己的
   注释里已经提到、并主动绕开的同一个问题。把解压出来的 `bin/ycsb`（第三方发行包
   的一部分，不在本仓库版本控制中）换成一个转发到 `ycsb.sh` 的 shim 后解决。
