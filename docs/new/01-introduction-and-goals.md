# 1. 引言与目标

> arc42 §1 Introduction and Goals。本章回答三个问题：这个系统要解决什么问题、
> 什么质量比什么更重要、谁会读这份文档以及他们分别关心什么。后续 11 章都是在
> 回答"怎么做到"，本章先回答"为什么要做、做到什么程度算好"。

## 1.1 需求概述

标准 Redis 的内存分配（`malloc`/jemalloc）完全不知道 NUMA 拓扑：一个 key 可能被
分配在离处理它的 CPU 核心很远的内存节点上，每次访问都要多付出跨节点延迟；分配器
也没有任何机制区分"这个 key 很热，应该留在快速内存"和"这个 key 很冷，可以放到
慢速、容量更大的内存"。

CXL（Compute Express Link）的出现放大了这个问题的价值：CXL.mem 让操作系统可以把
一块挂在 PCIe 总线上的内存当作普通内存使用，但它的延迟通常是本地 DRAM 的数倍、
带宽也更低。从系统软件的视角看，一块 CXL 内存基本上就是"又多了一个比传统远端
socket 内存更慢、但容量可以做得更大的 NUMA 节点"——这正是本项目把"如何用好 CXL
扩展内存"重新表述为"如何用好一个更慢的 NUMA 节点"的原因：不需要为 CXL 发明一套
全新概念，只需要把"热数据留在本地节点、冷数据迁到远端节点"这套 NUMA 调度逻辑，
扩展到"本地 DRAM 节点 vs. CXL 慢速节点"这个场景。

本项目要构建的，就是一套**在完整保留 Redis 原有 API 兼容性的前提下**，能够：

1. 按 NUMA 节点粒度分配内存；
2. 持续追踪每个 key 的访问热度；
3. 依据热度、NUMA 拓扑与节点资源压力，自动、可插拔地在节点间迁移数据——热数据
   往快速节点靠，冷数据往慢速（CXL）节点靠；
4. 把上述调度逻辑抽象成可独立评测、可替换的策略，而不是写死在内核里的一段代码。

## 1.2 质量目标

按优先级从高到低排列——排在前面的目标，在设计出现冲突时优先满足：

| 优先级 | 质量目标 | 含义 | 现状证据 |
| --- | --- | --- | --- |
| 1 | **API 完全兼容** | 客户端不需要感知任何 NUMA/CXL 相关改动就能正常使用 Redis；新增能力只通过独立的 `NUMA` 命令暴露 | `make test` 跑通完整的标准 Tcl 测试套件（91/91），未修改任何标准命令的对外行为 |
| 2 | **正确性优先于速度** | 迁移、分配路径宁可保守也不能破坏数据；性能优化不能以牺牲原子性/一致性为代价 | `numa_key_migrate` 对全部 5 种数据类型的全部编码都有专门适配器，而不是"先支持常见情况" |
| 3 | **可验证性** | 任何性能或行为声明必须能通过实际运行的测试复现，不接受纸面估算 | 全部测试脚本遵循"环境不满足就诚实跳过并写明原因，绝不伪造通过"的统一原则（见 `TESTING.md`） |
| 4 | **迁移开销可控** | 后台迁移不能显著拖慢主事件循环；扫描/迁移都有预算和渐进式设计 | Composite LRU 的兜底通道按 `scan_batch_size` 渐进扫描而非一次性全表扫描；AE 调度模式下 `execute_step()` 接受 `deadline_us`/`budget` 参数 |
| 5 | **可插拔与可评测性** | 调度策略应该是可替换的组件，而不是唯一写死的实现，且新策略要能在没有真实多节点硬件时被公平评测 | 16 槎位策略框架 + 独立的 NUMAflow 子系统（36 个原子操作、确定性公平评测框架） |
| 6 | **诚实的工程记录** | 文档记录真实发生的问题（合并引入的 bug、验证失败的实验），而不是理想化的设计叙述 | `docs/redis7-migration.md` 逐条记录 6 个合并静默引入的 bug；`ARCHITECTURE.md` 记录 CXLMemSim guest 验证受阻于自定义内核的真实结论 |
