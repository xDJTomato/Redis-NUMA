# 4 基于YCSB与QEMU的Redis-NUMA功能验证与压力测试

## 4.1 压力测试环境

### A. 系统基本信息

为验证Redis-NUMA系统在分层非一致访问内存环境下的功能正确性和性能表现，本项目构建了基于QEMU的模拟测试环境和基于双路NUMA服务器的实际压力测试环境。QEMU环境用于复现实验过程中的CXL分层内存拓扑，使系统能够在可控条件下验证NUMA节点识别、远端内存分配、键值迁移和策略调度等基础功能；实际服务器环境用于执行高并发YCSB压力测试，评估系统在接近真实部署条件下的吞吐量、内存占用和迁移稳定性。

测试系统以Redis 6.2.21为基础版本，编译时启用HAVE_NUMA条件编译宏并链接libnuma库。由于本项目在zmalloc.c中实现了NUMA感知的统一内存入口，并在Slab分配器内部维护节点粒度的内存池，构建过程固定使用libc作为底层分配器，避免jemalloc自身的arena管理机制与项目实现的NUMA分配策略发生冲突。Redis-NUMA服务端启动后，首先通过libnuma接口检测系统可用节点，读取节点距离矩阵和当前CPU所在节点，再初始化Slab分配器、可配置策略框架、键值迁移引擎、Composite LRU策略和带宽监控模块。

实际压力测试环境采用多NUMA节点服务器，其中本地DRAM节点用于承载热数据和Redis主线程主要访问路径，远端节点用于模拟CXL扩展内存。测试过程中将Redis-NUMA进程限制在指定CPU节点集合内运行，使其访问本地节点和远端节点时能够形成稳定的非一致访问延迟差异。对照组使用未启用NUMA扩展的原始Redis版本，在相同硬件、相同YCSB负载和相同客户端线程数下运行，以便比较Redis-NUMA引入的内存管理和迁移逻辑对吞吐量与内存占用的影响。

### B. 测试负载与流程

本项目采用YCSB作为主要压力测试工具。YCSB（Yahoo! Cloud Serving Benchmark）是面向云服务与键值数据库系统的通用基准测试框架，其设计目标是在统一的客户端、负载生成器和指标采集模型下，对不同数据库系统的服务能力进行可重复比较。YCSB将测试过程抽象为两个阶段：加载阶段负责向数据库写入指定数量的初始记录，事务阶段按照预设的读写比例、访问分布和字段大小持续发起操作，并统计吞吐量、平均延迟、分位延迟和操作成功率等指标。对于Redis这类内存键值数据库而言，YCSB能够以较低的工具复杂度生成稳定的高并发读写压力，因此适合作为本项目验证内存分配路径、热度追踪路径和后台迁移路径的统一测试入口。

YCSB的数据模型由记录、字段和值三部分构成。每条记录对应Redis中的一个键，记录内部可以包含一个或多个字段，每个字段对应一段定长或可配置长度的字符串值。在Redis绑定中，YCSB客户端会将记录转换为Redis字符串或哈希结构进行写入。本项目的测试重点是观察Redis-NUMA对中等大小value对象的分配行为，因此选用字符串类型键值作为主要对象模型，并将字段大小设置为8KB。该设置既能模拟实际缓存系统中较常见的中等大小负载，又能放大内存分配器在页面对齐、Slab内部碎片和NUMA节点选择方面的差异。

YCSB的负载配置由若干核心参数控制。recordcount决定加载阶段写入的总记录数，operationcount决定事务阶段执行的操作总数，threadcount决定客户端并发线程数量，fieldlength决定每个字段的字节长度，readproportion、updateproportion和insertproportion决定读、更新和插入操作的比例，requestdistribution决定键值访问分布。本项目将记录数量设置为100万条、字段大小设置为8KB、客户端线程数设置为64，使数据集规模达到GB级并形成持续并发压力。在热点访问阶段，测试使用非均匀访问分布，使少量键值获得更高访问频率，从而触发Redis-NUMA的热度累积、候选池写入和热数据拉回逻辑。

完整测试流程分为三个阶段。第一阶段为填充阶段，YCSB向Redis连续写入100万条8KB键值数据，用于观察系统在大规模写入时的节点分配行为、Slab路径与Direct路径占比、used_memory与RSS之间的关系。第二阶段为热点访问阶段，YCSB按照热点分布对已有键值执行读写操作，用于验证热度追踪模块能否在业务访问路径中正确更新PREFIX元数据，并触发Composite LRU策略将远端热数据迁移回本地节点。第三阶段为持续压力阶段，在维持较高并发访问的同时继续观察系统的迁移速率、节点实时占用、带宽压力和吞吐量变化，用于评估后台策略调度在长时间运行条件下的稳定性。

测试脚本在每个阶段开始和结束时采集Redis INFO memory输出、NUMA CONFIG STATS输出、迁移统计信息和系统层RSS数据。其中，NUMA CONFIG STATS采用扁平key-value格式输出各节点累计分配次数、累计分配字节数和实时占用字节数，同时输出Slab路径与Direct路径的实时字节数和分配次数。该格式便于脚本在非交互模式下稳定解析，也能够直接反映8KB对象是否进入Slab路径以及各节点实时占用统计是否保持为正值。

### C. 压力测试

在早期实现中，Slab分配器仅覆盖8字节至4KB范围内的小对象，超过4KB的对象全部进入直接NUMA分配路径。YCSB默认8KB字段在Redis内部加上PREFIX后略大于8192字节，直接调用libnuma分配时会触发mmap系统调用，而Linux内核以4KB页面为单位管理虚拟内存区域，因此每个8KB对象会被向上对齐到3个页面，实际占用12288字节左右的物理内存。对于100万条记录，该页面对齐行为会带来约3.9GB额外RSS占用，使Redis报告的逻辑内存与操作系统观察到的物理内存之间出现明显偏差，并在内存受限场景下提高OOM风险。

针对上述问题，最终实现将Slab分配器扩展到8字节至64KB范围，并引入小Slab和大Slab两级结构。不超过4KB的对象继续使用64KB小Slab；大于4KB且不超过64KB的对象使用2MB大Slab。大Slab通过mmap申请较大的虚拟地址空间，截取2MB对齐区域后释放未对齐的头尾部分，再将该区域绑定到目标NUMA节点，并在其内部按大小等级细分对象槽位。该方案将原本逐对象发生的页面对齐浪费转化为Slab内部的紧凑分配，使8KB对象能够连续复用2MB区域内的槽位。

压力测试结果显示，在填充阶段结束后，Redis-NUMA的8KB键值数据主要进入Slab路径，Direct路径仅保留少量超大对象和内部管理对象。NUMA CONFIG STATS输出中，远端节点实时占用约为8GB量级，Slab路径实时字节数约为8.7GB，而Direct路径实时字节数仅为十余MB，说明8KB value已经不再通过逐对象mmap分配。与此同时，各节点live统计均保持为正值，表明线程局部缓存的统计管线修复后，used_memory_node不再因缓存命中、缓存回收和迁移过程中的节点标识变化而出现负值。

从吞吐量角度看，Redis-NUMA在加入大Slab和线程局部缓存后，与原始Redis版本之间的性能差距明显收敛。填充阶段两者吞吐量基本接近，说明Slab路径消除了逐对象mmap带来的主要写入开销；热点访问阶段和持续压力阶段中，Redis-NUMA需要额外执行热度更新、候选池维护和后台迁移决策，因此仍存在少量开销，但该开销保持在可接受范围内。测试过程中三个阶段均能够完整运行，没有出现早期实现中由于RSS膨胀导致的中止现象，说明扩展后的Slab分配器能够支撑8KB中等对象负载下的持续运行。

综合来看，压力测试验证了Redis-NUMA系统的三个核心性质。第一，NUMA感知分配路径能够按照策略将新对象分布到本地节点和远端节点，并通过PREFIX维护对象级元数据；第二，键值热度追踪和Composite LRU策略能够在业务访问过程中识别热点并触发迁移；第三，扩展后的Slab分配器能够有效降低中等大小对象的页面对齐浪费，使系统在CXL分层内存场景下保持较低的物理内存放大和较稳定的吞吐量表现。
