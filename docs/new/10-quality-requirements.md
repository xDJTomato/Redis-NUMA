# 10. 质量目标（Quality Requirements）

> arc42 第 10 章。本章把项目关心的质量属性，拆解成一组可验证的具体场景
> （刺激 → 响应），而不是停留在"要快""要稳"这类无法验证的口号上。

## 10.1 质量树

| 优先级 | 质量目标 | 说明 |
| --- | --- | --- |
| 1 | 正确性与 API 兼容性 | 加了一整套 NUMA/CXL 能力，但对客户端而言必须还是"同一个 Redis" |
| 2 | 性能：迁移与分配开销可控 | 热/冷数据搬迁不能把它本该省下的延迟又搭进新的开销里 |
| 3 | 可测试性与诚实降级 | 环境不满足某项前提时，必须明确说"跳过"，绝不伪造"通过" |
| 4 | 可维护性与可扩展性 | 新增一个模块、一条策略、一个原子操作，代价应该是可预期的 |
| 5 | 可观测性 | 运维/开发者能在不重启进程的前提下看清系统内部状态 |

## 10.2 场景

### 质量目标 1：正确性与 API 兼容性

**场景 Q1-1**
- 刺激：对本 fork 的 `redis-server` 执行任意标准 Redis 客户端能发出的命令（`NUMA` 系列命令除外）。
- 响应：行为与上游 Redis 7.2.6 完全一致；`make test` 完整 Tcl 套件（91/91）必须全部通过。

**场景 Q1-2**
- 刺激：对 Redis 核心做一次跨版本合并（如本项目实际执行的 6.2.21→7.2.6），且合并过程中没有留下任何 `<<<<<<<` 冲突标记。
- 响应："没有冲突标记"不能被当作"合并正确"的证据；必须以真实的 `make -j$(nproc)` 编译到底 + 完整测试套件通过作为唯一验收标准。这条要求不是理论上的谨慎——本项目的真实合并里，6 个行为改变型 bug 全部是零冲突标记地混入代码的，只有编译和测试真正抓住了它们（详见 [`redis7-migration.md`](../redis7-migration.md)）。

**场景 Q1-3**
- 刺激：一个新的 NUMA 模块被接入 `numa_init()`/`initServer()` 的启动顺序。
- 响应：任何初始化顺序错误（如迁移模块在分配器初始化完成前被调用）必须在启动阶段就可观察地失败，而不是延迟到某次不相关的操作中才崩溃。

### 质量目标 2：性能——迁移与分配开销可控

**场景 Q2-1**
- 刺激：NUMAflow 默认工作流（CAAT，`numa_flow_cron()` 按 `numa-flow-interval-sec` 触发）在一次执行里枚举整个 keyspace 并决定迁移。
- 响应：单次执行的迁移数量受 NUMAflow 执行上下文的 `budget`（默认 256）约束，不允许无限制地把一次执行拖长；淘汰路径上的降级另受 `numa-demote-max-migrate` 约束。

**场景 Q2-2**
- 刺激：工作负载呈现明显的热点分布（如 Zipfian，多数访问集中在少量 key 上）。
- 响应：CAAT 策略下的净代价（访问代价 + 迁移代价）必须低于既有基线。已实测数据（zipf / 3000 key / 12 万次访问 / DRAM 容量约束在工作集 50%）：CAAT 净代价比 TinyLFU 低约 20%，比 Composite LRU 低约 37%，本地命中率约 91%。但这个优势是**工作负载依赖**的，不是无条件成立——在 uniform（访问接近均匀分布）负载下 CAAT 净代价反而比 Composite LRU 高约 31%（详见 [ADR-09](09-architecture-decisions.md) 的复测记录、[`docs/numaflow/README.md`](../numaflow/README.md)）。

**场景 Q2-3**
- 刺激：DRAM 节点写满，且线上持续有新的热点数据需要晋升。
- 响应：调度策略必须具备"降级腾位"的能力（不能只升不降），否则热点数据晋升会在 DRAM 写满后完全停滞——这正是 CAAT 相对于 Composite LRU / TinyLFU 的关键改进点。

**场景 Q2-4**
- 刺激：`redis-cli --cluster create` 或其它非 `redis-server` 二进制执行大量 dict 分配。
- 响应：这些二进制从未调用 `numa_init()`，因此必须安全退化为普通 `malloc` 路径，而不是在未初始化的全局状态上运行 slab 分配器逻辑（这条要求来自一个真实的历史 bug，见 11.6）。

### 质量目标 3：可测试性与诚实降级

**场景 Q3-1**
- 刺激：运行环境缺少某项可选依赖（JDK、`/dev/kvm`、`external/CXLMemSim` 未构建等）。
- 响应：`run_full_validation.sh` 及各独立测试脚本必须以 `skipped` 状态 + 明确原因退出（退出码 0，写入结果 JSON），绝不静默跳过或伪造一个"通过"的结果。

**场景 Q3-2**
- 刺激：CXLMemSim 的 CXL Type2 设备在 QEMU 客户机中完成 PCI 枚举，但内核驱动绑定失败。
- 响应：文档必须准确描述"走到哪一步、卡在哪一步、为什么"（本项目实际做法：记录到具体的 PCI 设备号、`bind` 报错、CXLMemSim 自身脚本里定制内核路径的证据），而不是笼统地写"未实现"或反过来夸大为"已验证"。

**场景 Q3-3**
- 刺激：一次基准测试脚本的默认参数（如 `--process-nodes 0,2`）与当前主机的真实 NUMA 拓扑（只有 1 个节点）不匹配。
- 响应：脚本应当报出清晰的错误（而不是静默使用错误的绑定），并提供可用的覆盖开关（如 `--process-nodes all`）。

### 质量目标 4：可维护性与可扩展性

**场景 Q4-1**
- 刺激：需要新增一个 NUMA 模块。
- 响应：遵循 [`CONTRIBUTING.md`](../../CONTRIBUTING.md) 的固定六步流程（建 `.h`/`.c` → 加入 `Makefile` 的 `REDIS_SERVER_OBJ` → `server.h` 包含 → `server.c` 中按依赖顺序初始化 → 使用 `_serverLog` 而非 `serverLog` → 遵守模块依赖顺序）即可完成集成，无需改动既有模块内部逻辑。

**场景 Q4-2**
- 刺激：需要试验一种新的迁移/分配策略。
- 响应：可以完全在 NUMAflow 子系统（纯 C11，零 Redis/libnuma 依赖）中用原子操作拼出新策略、跑公平评测验证效果，再决定是否通过 `NUMA FLOW LOAD` 接入线上 Redis 进程，全程不需要真实 NUMA 硬件、不需要重新编译内核。

### 质量目标 5：可观测性

**场景 Q5-1**
- 刺激：运维人员需要在不重启服务的情况下判断当前 NUMA 子系统的健康状态。
- 响应：`NUMA CONFIG STATS`（每节点分配统计）、`NUMA MIGRATE STATS`（迁移统计）、`NUMA FLOW LIST/STATUS`（各已加载工作流的状态与反馈）均可在线查询，且 `NUMA FLOW DEFAULT <name>`/`NUMA FLOW LOAD` 支持不重启切换或热加载迁移策略。
